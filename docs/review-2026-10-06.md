# AMIRA MCP server review — 6 October 2026

> **Implementation status:** implemented in version 1.19.0, except WissKI links and
> licence/access-rights filters, which were set aside. See the
> [implementation report](implementation-2026-10-06.md). The findings below preserve
> the original audit. Two corrections made during implementation: P1 #10 was
> already fixed in v1.18 (related projects carry `omeka_id` and `amira_url`); the
> session's connector, which ran an older release, had shown the stale shape. And
> the host nginx in front of the deployment already limits each real client IP to
> 60 requests per minute (`omeka-s-docker/deploy/amira/MCP_HOST_NGINX.md`), so the
> shared in-process bucket throttled legitimate users collectively rather than
> leaving the endpoint unprotected.

Follow-up to the [5 October review](review-2026-10-05.md) and its
[implementation in v1.18.0/1.18.1](implementation-2026-10-05.md). Everything below
is **new**: findings already reported or fixed yesterday are not repeated.

The foundation remains sound: one typed offline snapshot behind both transports,
the modern 2026-07-28 entries, snapshot-owned indexes, bounded text windows. The
gaps found today sit in four places. Operations: the public endpoint lags the
code and its rate limiter misidentifies clients. Matching semantics: country,
punctuation, whitespace and IDs. The local release gate. And data the crawl
already pays for but never surfaces.

**Method.** The work ran as four review passes plus spot verification:

- tool layer, by code reading and in-process calls;
- tests, CI and packaging, including a per-module coverage build;
- feature gaps against the live Omeka API, about 45 small requests;
- current upstream documentation and registries.

All findings were checked against the bundled 9 September snapshot. Tool calls
used the in-memory SDK client with `AMIRA_LIVE_REFRESH=0` and an isolated cache.
Items marked **(repro)** were reproduced independently. Baseline: `npm run
typecheck` passes, and **133/133 unit tests** pass on Node 24.19.0. No code was
changed, committed or deployed.

## P0: operations (hours of work, user-visible today)

### 1. The public endpoint still runs v1.17.0 (repro)

`POST https://data.africamultiple.uni-bayreuth.de/mcp` reports
`serverInfo.version: "1.17.0"` and **29 tools**. None of the v1.18 work is live:
the six research tools, the seven Apps on the official SDK, durable refresh and
profiles. `omeka-s-docker/compose.amira.yml` still defaults
`AMIRA_MCP_VERSION:-v1.12.0`.

The AMIRA connector attached to this Claude session is older still. It has no
`list_publication_facets`, and its description says "~280 publications" against
555 live.

**Action:**
- Bump the `.env` pin to v1.18.1 (or the next fix release) and redeploy.
- Reconnect the ChatGPT connector so it re-reads the reshaped schemas.
- Update the compose default so a fresh host does not boot v1.12.0.

### 2. Every public user shares one rate-limit bucket

`compose.amira.yml` does not set `AMIRA_TRUST_PROXY`. Every request therefore
reaches the server from the nginx container's IP, and
[`clientKey`](../src/http.ts) keys all public traffic to **one** 120 req/min
bucket. A single busy ChatGPT session can throttle every other user.

Enabling `AMIRA_TRUST_PROXY` as written does not fix it.
[`clientKey`](../src/http.ts) takes the **leftmost** `X-Forwarded-For` entry,
and nginx sends `$proxy_add_x_forwarded_for`
(`omeka-s-docker/deploy/amira/nginx-mcp-location.conf`).
That header is the client's own XFF with the real address appended, so the
leftmost entry is attacker-chosen.

**Fix:**
- Key on `X-Real-IP`, which nginx sets to `$remote_addr`, or on the rightmost
  XFF hop (an `AMIRA_TRUSTED_HOPS=1` count).
- Then enable it in compose.
- Optionally bucket IPv6 by /64.
- Add a unit test with a forged leftmost XFF.

### 3. Claude Code truncates the server instructions mid-citation-rules (repro)

[Claude Code](https://code.claude.com/docs/en/mcp) truncates each server's
`instructions` at **2,048 characters**. `INSTRUCTIONS` in
[`mcpServer.ts`](../src/mcpServer.ts) is **3,327** characters, and the CITATIONS
block starts at character 1,658. The cut falls just before "NEVER print legacy
DRE identifiers", so these rules never reach Claude Code users:

- "never print legacy DRE identifiers";
- "use only URLs returned by the tools";
- the `Surname, Forename` name rule;
- the "absence is not proof" caveat.

**Fix:** put CITATIONS and NAMES first and compress the institutional prose. The
AMRC list belongs in the skill's `cluster-context.md` and in
`get_collection_overview`. Add a test that `INSTRUCTIONS.length <= 2048`.

### 4. Release-gate and packaging hygiene

- **The local gate measures your cache, not the shipped snapshot.**
  - `smoke-test.mjs`, `smoke-http-test.mjs`, `scripts/weigh.mjs` and
    `scripts/preview-apps.mjs` never isolate `AMIRA_CACHE_DIR`.
  - `weigh.mjs` uses `??=` for `AMIRA_LIVE_REFRESH`, so an exported `=1` would
    start a crawl.
  - `loadInitial` prefers the newer snapshot. So locally the 16 September cache
    (555 publications) outranks the bundled 9 September snapshot (562) that
    ships in the `.mcpb`.
  - **`test/token-baseline.json` was generated from that cache.** Against the
    bundled snapshot, `weigh --check` reports 9 drift notes, up to +15.7%.
  - CI is unaffected because its runners start empty.
  - **Fix:** one shared env helper that isolates the cache and clears every
    `AMIRA_*` variable. Also record `fetchedAt` / `snapshot_id` in the baseline
    and fail on mismatch.
- **The `.mcpb` ships ~1.1 MB (compressed) of dead weight.** It contains
  `server/http.js` (2.58 MB), `server/lib.js` (2.48 MB), `server/fetchCli.js`,
  the whole `docs/` folder (reviews, benchmarks) and the `Dockerfile`. Add them to
  `.mcpbignore`, and add a packaging test that checks the *real* archive
  against an allowlist.
- **The Docker base image is not digest-pinned.** The README and yesterday's
  implementation report say it is, but `Dockerfile` uses plain `node:26-slim`
  twice, and Dependabot has no `docker` ecosystem entry. Pin
  `node:26-slim@sha256:…` and add the ecosystem, or correct the README.
- **`package.json` author is mojibake** (`FrÃ©dÃ©rick`), introduced in v1.18.0
  by an encoding round-trip. `manifest.json`, `CITATION.cff` and `.zenodo.json`
  are correct, but `package.json` ships inside the `.mcpb`.
- **Working-tree line endings.** Git stores LF, but 41 working files are CRLF
  and 15 mixed, including three skill files. Local builds therefore hash
  different skill bytes than CI: `SKILL.md` is 18,722 bytes locally against
  18,464 in Git, so the digests differ. Run `git add --renormalize .` after
  setting `core.autocrlf=false`, or re-checkout, and add `.editorconfig`.
- **The `data-latest` release is stale.** Its tag still points at `ef6ac93`
  (June). It still carries the pre-rename `africa-multiple-mcp-server.mcpb`
  and `generatedAt.txt` from 8 June. Delete the orphaned assets and move the tag.
  `snapshot-signature.mjs` hashes data only, so code fixes never refresh it.

## P2: contracts, host behaviour and performance

### Result size versus Claude Code and ChatGPT limits

Claude Code persists any text result over **50,000 characters** to a file, warns
at 10k tokens and caps at 25k (`MAX_MCP_OUTPUT_TOKENS`). From the token baseline:

- `search_research_items@max`: 59,808 chars;
- `get_entity_graph@max`: 59,022 chars.

Both exceed the file threshold. `list_subjects@max` and `search_publications@max`
(~44k chars) cross the warning.

**Options, in order of preference:**

1. Lower the maximum `limit` or slim the max-mode summaries until every result
   stays under 45k chars. Assert this in `weigh --check` as a hard gate beside
   the 20k-token ceiling.
2. Offer an export/`resource_link` path for bulk results (see Features §8).
3. As a last resort, declare `_meta["anthropic/maxResultSizeChars"]` on the two
   tools.

The [MCP roadmap](https://modelcontextprotocol.io/development/roadmap) also lists
a redesign of the duplicated `content` plus `structuredContent` result shape.
Keep `textResult` centralised so that change lands in one file.

### Host-specific discovery hints

- **Claude Code defers tool loading by default** (tool search).
  `_meta["anthropic/alwaysLoad"]: true` keeps a tool loaded up front. Put it on
  `get_collection_overview` and `resolve_entity`, the entry points the
  instructions tell the model to call first. Tool search also matches argument
  names and descriptions, so the parameter descriptions earn their bytes.
- **ChatGPT re-renders the iframe too often when UI is attached to data tools.**
  OpenAI's [UI guidance](https://developers.openai.com/plugins/build/chatgpt-ui.md)
  is that only render tools carry `_meta.ui.resourceUri`. AMIRA attaches apps to
  `search_publications`, `list_locations` and `find_related`, whose primary job
  is data. Keep the apps on the visual-first tools (overview, timeline,
  sections, entity graph). Then measure in ChatGPT before deciding whether the
  other three need dedicated render tools, which would cost discovery tokens.
- **App downloads are a draft-spec feature.** `bridge.ts` calls
  `app.downloadFile` unconditionally, but download-file exists only in the Apps
  *draft*. Check the host capability first and fall back to copy-to-clipboard
  or a visible text block.
- **Profiles hide tools but not their apps.** `AMIRA_TOOL_PROFILE=discovery`
  still lists all seven `ui://` resources. Calling a disabled tool returns a
  `-32602` protocol error instead of a tool error.
  - `configureToolRegistration` monkey-patches `server.registerTool`. Instead,
    pass the profile into `registerTools` and call `RegisteredTool.remove()`,
    which is public SDK API, on excluded handles. Filter the app resources the
    same way.
- **`annotations.title` duplicates `title` with different wording** on all 35
  tools. Hosts prefer `title`, so the annotation copy is pure discovery cost
  (~250 tokens). Keep `readOnlyHint`, `destructiveHint` and `openWorldHint`,
  which OpenAI's review checks explicitly.

### Contract consistency

- **Error results violate the output schemas.** `isError` results put
  `{error}` into `structuredContent`, which fails 10 of the 11 output schemas;
  only `fetch` models the error. The v2 client skips validation on errors, but
  other clients may not. Omit `structuredContent` on errors, or add an error
  branch to each schema.
- **ID shapes vary.**
  - Podcast and video rows and `get_podcast`/`get_video` return a numeric `id`
    with no `omeka_id`. `list_collections` returns a numeric `id`.
    `list_institutions` and `list_groups` rows carry no ID at all.
  - `get_institution` and `get_research_section` accept only `name`, although
    `resolve_entity` hands out IDs.
  - Standardise on `{id: string, omeka_id: number}` per row, and accept `id` on
    every `get_*`.
- **Two limit contracts coexist.** Older tools clamp and echo
  `requested_limit`/`effective_limit`. The v1.18 tools reject over-limit values
  through the schema ("Too big"), and `search` clamps without echoing. Pick one
  (clamp and echo is friendlier to models) and share `limitParam`/`offsetParam`.
- **The `search_*` `keyword` is one literal phrase.**
  `keyword="Kunst und Architektur"` → 0, while `search` tokenizes the same
  query. Either AND the tokens or say "literal phrase" in the parameter
  description.
- **Descriptions drift from behaviour.**
  - `get_project` promises "sample research items" and returns none.
  - `list_institutions` says "by name, country or affiliation" but matches the
    name only.
  - `get_research_section` promises items and returns a count.
- **Set `maxToolInputElements`** (SDK 2.3.0 `McpServer` option). It caps array
  and object sizes before schema validation and complements the existing string
  bounds.

### Search ranking (feeds the planned retrieval evaluation)

- **Ties keep corpus order.** `search("music", limit 50)` returns **50 research
  items and 0 publications or videos**, although a publication title contains
  "Music" (repro). Interleave corpora or add an IDF-weighted tie-break.
- **Substring matching rewards fragments.** "art" hits "Zeitungs*art*ikel", and
  in "Kunst und Architektur", "und" scores via "Urk*und*e". Match at token
  starts.
- **Stopwords are English and French only.** Add German and Portuguese, the
  collection's other main languages.

Measure these against a judged query set before changing the ranker, as
yesterday's review recommended. They are the obvious first cases for it.

### Performance (repro, warm, in-process)

| Path | Measured | Cause → fix |
|---|---|---|
| `get_snapshot_changes` with no history | **0.9–1.5 s** per call | Reloads the bundled snapshot and every retained generation from disk, then diffs with `JSON.stringify` on every page → cache the loaded generations and the per-`(from,to)` diff on the store. |
| `list_groups` (default) | **240–285 ms** | Rescans all items per row with `equalsCI`, folding both sides → contributor index by Omeka ID and folded name on the store. |
| `get_text_passages`, one 842k-char text, no match | **190–250 ms** (≈5 s cold) | `foldedRanges` rebuilds offset arrays per call → early exit on `foldCached(text).includes(…)`, cached range index. The 1,000-match cap also makes later matches unreachable while reporting `has_more:false`. |
| `get_entity_graph` evidence page on a busy node | ~120 ms per page | Recomputes `entityEdges` with SHA-256 per link → cache edges per seed. |

## P3: refactoring and cleanup

- **Layering is inverted.** The core query modules (`researchItemQuery.ts`,
  `publicationQuery.ts`, `searchRanking.ts`, `publicationExport.ts`) import from
  `tools/_shared.js`, and two of them build MCP results. Move the matching
  helpers into core, return typed errors, and let the tool layer render them.
- **Duplication worth collapsing:**
  - `search_podcasts`/`search_videos` and `get_podcast`/`get_video` are
    near-copies (`media.ts`).
  - The `nameMatchesQuery || containsCI` person match exists 7 times.
  - University matching exists twice, and only one copy trims.
  - Year-range validation exists in four variants with different messages.
  - `ui://` URIs are hard-coded in `facets.ts`, `publications.ts` and
    `research.ts`.
  - `fetchDoc` in `openai.ts` re-implements the projections of six `get_*`
    tools; share the projection functions.
- **Sections link to projects by label, not ID** (`researchSections.ts:42,71`,
  `data.ts`). Counts agree today, but a section rename would silently orphan
  projects.
- **Stale comments and dead code:**
  - `index.ts` says "the 26 rich tools" (there are 33).
  - `exposure.ts` cites the deleted `BENCHMARK_EVALUATION_PLAN.md`.
  - `apps.ts` says the UI templates are "the only resources" (skill files are
    served too).
  - The `summaries.ts` header describes the old barrel.
  - `toolProfiles.ts:21-22` and `openai.ts:38` have orphaned comments.
  - `mcpServer.ts` has an import above its file header.
  - `omekaJSON.ts` `templateId` is unused.
- `get_research_item` truncates the table of contents without a flag.
  Identifiers count as *descriptive* in the keyword index but *structured* in
  the ranker. Pick one.

## Testing and CI

**Coverage.** A per-module esbuild build gives meaningful numbers; the single
bundle plus sourcemaps under-reports. All 133 tests pass:

- overall: **88.9% lines / 79.5% branches / 84.8% functions**;
- weakest: `tools/organizations` 46.5% lines, `tools/projects` 47.5%,
  `tools/researchSections` 52.3%, `tools/openai` 57.7% (fetch of
  items/projects/sections/podcasts), `tools/summaries` 69.5%, and `data.ts`
  background refresh and swap at 81%;
- unmeasured: `http.ts`, which runs only as a killed child process, and the
  ~690 lines of app renderer code inside template strings.

**Nine tools have no unit test** (smoke only): `get_institution`, `get_project`,
`get_research_section`, `list_categories`, `list_cluster_partners`,
`list_collections`, `list_groups`, `list_institutions`, `search_projects`. Three
more are thin: `search_persons`, `get_podcast`, `list_research_sections`.

**Test-quality issues:**
- **Environment leakage.** Only `AMIRA_EXPOSURE` is cleared, so
  `AMIRA_TOOL_PROFILE`, `AMIRA_SKILLS` or `AMIRA_SITE_*` in the shell change the
  results.
- **Temp directories are never removed.** `%TEMP%` holds 217 `amira-*` entries.
- **The HTTP smoke test uses fixed ports.** With 8799/8800 taken it talks to
  someone else's server and passes. `http.test.mjs` already uses `PORT=0`.
- **Output schemas are validated only by accident.** The client validates only
  after `tools/list` ran on the same connection, so `research.test.mjs`
  (the six v1.18 tools) never validates.
- **Assertions are brittle.**
  - Exact tool counts appear in three places.
  - Publication thresholds disagree: ≥240 in stdio smoke, ≥270 in HTTP smoke.
  - PR CI runs smoke against a fresh live crawl.
- **`test/evaluations/publications.xml` never runs.** It has 6 pairs;
  mcp-builder asks for 10.

**Top additions:**
1. A shared hermetic test env: isolated cache, all `AMIRA_*` cleared, temp
   cleanup.
2. Exact-assertion unit tests for the nine tools above, and for `fetch` on every
   record kind.
3. An explicit ajv test of all 11 output schemas at all four exposure levels,
   including error results.
4. Background refresh: swap, abort on stop, old store kept on failure.
5. An exported HTTP request handler tested in-process: Origin/Host, CORS, 413,
   rate-limit key incl. forged XFF.
6. Run the app renderers in `node:vm` or happy-dom: empty and
   publications-only states.
7. Golden files for `tools/list` and fixture outputs, with an `--update` flag.
8. fast-check properties: fold/offset round-trip, pagination never skips or
   repeats, BibTeX/RIS/CSL well-formedness.
9. A real-artifact packaging test: file allowlist, one author everywhere, tag ==
   version.
10. Replay the evaluation XML's exact answers as a deterministic `node:test`
    against the pinned snapshot, and grow it to cover every corpus.

**External harnesses:**
- Run the official [conformance suite](https://github.com/modelcontextprotocol/conformance)
  as a non-blocking CI job against the container:
  `npx @modelcontextprotocol/conformance@0.2.0-alpha.12 server --url
  http://127.0.0.1:8787/mcp --requirements 2026-07-28` with an expected-failures
  baseline. Use the alpha: `latest` (0.1.16, March) predates 2026-07-28.
- Inspector 2.9.0 CLI `skills/list --verify --require-digests` checks the Skills
  contract that ChatGPT's importer verifies.

**CI/CD:**
- **Permissions are too broad.** `release.yml` and `refresh-data.yml` grant
  write to the whole job, and `refresh-data.yml` exposes `GH_TOKEN` in
  workflow-wide env, visible to `npm ci` install scripts and the crawl. Split
  into a read-only build job and a write-scoped publish job. Scope the token to
  single steps and set `persist-credentials: false`.
- **No timeouts.** No workflow sets `timeout-minutes`, and the live tests' fetch
  has no timeout, so a hung Omeka request can hold a job for 6 hours. Add
  `--test-timeout` to `scripts/test.mjs` as well.
- **No version check on release.** Nothing checks that the tag equals the
  `package.json` version.
- **Provenance.** With MCPB signing gone, add `actions/attest-build-provenance`
  for the `.mcpb` and skill zip. The new MCP
  [local-server security guide](https://modelcontextprotocol.io/docs/tutorials/security/local-server-security)
  asks for exactly this.
- **Minor:**
  - Typecheck runs in all four matrix lanes.
  - Release runs the unit tests twice and builds three times.
  - Actions are tag-pinned, not SHA-pinned (the sibling `omeka-s-docker`
    already SHA-pins).
  - `ubuntu-latest` moves to Ubuntu 26 on 19 October.
- **Node.**
  - 26 becomes Active LTS on 28 October; 24 enters maintenance on 20 October.
  - 20 has been EOL since 30 April. `engines >=20` matches every MCP SDK
    package, so keep it only while the Node 20 CI lane stays.
  - Moving the matrix to 22/24/26 is reasonable.
