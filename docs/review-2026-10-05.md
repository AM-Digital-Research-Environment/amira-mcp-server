# AMIRA MCP server review — 5 October 2026

> Implementation status: the approved work is implemented in version 1.18.0.
> See the [implementation report](implementation-2026-10-05.md) for final behavior,
> measurements and validation. Findings and proposed limits below preserve the
> original audit; they do not describe the current implementation.


The architecture is a good fit for this collection: a typed, offline snapshot,
shared domain tools, two thin transports, bounded text retrieval, and source
citations. Keep that foundation. The highest-value work is to correct graph
semantics, make snapshot replacement and provenance safer, and cache repeated
derived data before adding more tools or an external search service.

This review covers source, tests, build/packaging, dependency registries, the
current MCP specification and SDK documentation. It includes measured queries
and two reproduced graph defects. Interoperability corrections and dependency
updates described below are implemented in this change; the larger proposals
are recommendations, not implemented features.

## Changes made during this review

- Updated all six outdated direct dependencies and refreshed compatible
  transitive dependencies. `npm outdated --json` now returns `{}`.
- Corrected the MCP App initialization payload to send `appInfo` and
  `appCapabilities` at the required level. A rejected handshake no longer sends
  a success notification. Theme changes from the parent frame are now applied.
- Included app presentation metadata in `resources/read` content, not only the
  resource listing.
- Updated the Skills extension manifests with raw byte sizes, added cache hints
  to `skills/get`, and made completion markers explicit. The SDK already stamps
  modern wire completion markers; their prior omission in handlers was not by
  itself a demonstrated wire failure. The missing sizes were a contract gap.
- Added tests against the actual modern stdio entry point and a modern HTTP
  client, alongside existing legacy coverage. The client SDK defaults to legacy
  negotiation, so upgrading the SDK alone does not exercise modern exchanges.
- Added [`npm run benchmark`](../scripts/benchmark.mjs) for reproducible offline
  latency and response-byte measurements.

## Prioritized findings

### P1 — Graph counts can overstate shared records

[`src/tools/related.ts`](../src/tools/related.ts) increments people once per
contributor role and countries once per place. Those are occurrence counts,
although the app calls them shared-item counts.

Reproduced against the bundled 9 September snapshot:

- `find_related(entity_type="person", value="Katharina Greven")` reports
  `Beier, Ulli: 104`; only **103 distinct items** credit both people.
- [Item 7398](https://data.africamultiple.uni-bayreuth.de/s/amira/item/7398)
  credits Beier as both collector and photographer.
- [Item 7684](https://data.africamultiple.uni-bayreuth.de/s/amira/item/7684)
  references Maasai Mara and Loita Hills; both roll up to Kenya, so one item
  increments that country twice.

Deduplicate each relation by entity ID within each source record before
counting. Preserve role occurrences separately when useful. Return distinct
`research_item_count` and `publication_count` for mixed-corpus relationships;
the current subject/person aggregates combine them. Add role-duplication,
multiple-places-in-one-country and author/editor fixtures. This must precede
any graph centrality or comparison features.

### P1 — The graph hides publication-only relationships

[`src/ui/related.ts`](../src/ui/related.ts) exits on `!d.matched_items`, even
when publications contributed relationships. With `value="decoloniality"`,
the tool returns **0 items and 5 publications**, but executing the renderer
produces “Nothing co-occurs with this seed in the collection.”

Use the combined eligible corpus count for the empty state, show both counts,
and label edge evidence accurately. This is separate from the counting defect.
The regression should run the actual renderer on a publication-only payload.

### P1 — Cached data can receive citations for the wrong configured site

[`loadInitial` / `tryLoad`](../src/data.ts) choose a snapshot by freshness without
checking `manifest.apiBase` against `config.apiBase`. Citation URLs are built
from the current configuration in [`src/urls.ts`](../src/urls.ts). Changing
`AMIRA_SITE_BASE` while retaining a cache can therefore attach another site's
URLs to old records.

Partition caches by normalized API origin/path and validate snapshot provenance
before serving either cache or bundled data. Define the deliberate offline
override behavior explicitly. Test two sites with overlapping Omeka IDs and
different record titles; reject cross-site attribution rather than silently
falling back to it.

### P2 — Cache promotion is validated, but replacement is not atomic

[`writeSnapshotAtomic`](../src/snapshot.ts) writes and verifies staging, then
removes the old destination before renaming. A rename failure loses the previous
disk cache; concurrent processes can race over the same destination. The
in-memory store and bundled fallback help availability but do not preserve the
last refreshed disk generation.

Use immutable generation directories, a small active-generation pointer and a
cross-process writer lock. Validate the candidate before publishing the pointer;
garbage-collect old generations afterward. Add failure injection around each
promotion step and competing-writer tests on Windows and Linux. The existing
name and README's “atomically promoted” language overstate the guarantee.

### P2 — Refresh does not cover every mutable corpus or expose operational state

[`probeRemote`](../src/snapshot.ts) observes item count and maximum item
modification time. Item-set descriptions and property labels can change without
changing that signature. Before/after probes detect some concurrent edits but
cannot make the crawl transactional. `fetchJSON` retries permanent 4xx errors
as well as transient failures and does not honor `Retry-After`.

Add item-set freshness and a periodic full-refresh ceiling; retry timeouts,
429 and selected 5xx responses with bounded jitter and `Retry-After`. Expose
refresh-in-progress, last attempt, last success and a sanitized failure class
in health/overview. Add cancellation and a shutdown deadline so an in-flight
crawl cannot prolong termination indefinitely. Keep serving the last good data.

### P2 — Repeated scans are the first useful efficiency refactor

Overview, facet and section handlers repeatedly derive stable aggregates from
the same snapshot. [`researchItems.ts`](../src/tools/researchItems.ts) computes
relaxation suggestions by scanning once for each omitted filter; worst-case
predicate work is O(N × F²). [`openai.ts`](../src/tools/openai.ts) rebuilds and
folds short field groups per query. The existing large-text fold cache helps,
but does not eliminate that work.

Build lazy derived indexes owned by each `DataStore`: canonical folded labels,
place ancestor chains, distinct facet counts, contributor-ID adjacency,
publication-author adjacency and pre-folded search field groups. Replacing the
store naturally replaces its caches. Cache aggregates, then format the response
under the current exposure policy; never reuse a full-exposure response for a
restricted exposure.

For relaxation suggestions, count failed predicates once per record: a record
failing exactly one active predicate contributes to that filter's suggestion.
Benchmark allocations and parity before introducing a database or search daemon.
HTTP constructs a server per request, so cache data on the store, not in a tool
registration closure. Keep independent transport instances for concurrent calls.

### P2 — Input and output contracts need targeted consistency

- Media searches accept inverted year ranges and return empty results, unlike
  research-item and publication searches, which report `invalid_range`.
- Free-text filters mostly lack length limits. The updated HTTP adapter has a
  4 MiB body bound, but that is far larger than a reasonable search query;
  expensive term scans and echoed filters can still consume substantial CPU
  and response space. Add shared query/identifier bounds and range validators.
- `find_related` caps `limit` without the `requested_limit` / `effective_limit`
  echo used by most other list tools.
- Only **3 of the 29 HTTP tools** advertise output schemas. This is permitted
  by MCP, but weakens generated clients and app validation. Start with overview,
  relationship and chart payloads; account for exposure variants and tool
  errors rather than imposing an inaccurate universal schema.
- [`foldedIndexOf`](../src/text.ts) falls back to accent-sensitive matching when
  folding changes string length. An NFD-form full text can match search but
  produce a null snippet. Use a folded-to-original offset map for snippets and
  test combining characters, not only precomposed accents.

### P2 — Authority identity should precede graph expansion

Name maps hold one record per folded label; facets and related lists also group
by label. `get_person` can resolve partial names to the first match. Two people
with the same label can be merged, and graph neighbors currently lack their own
IDs, links and evidence. A substring seed can match several subjects while its
single best-effort citation points to only one.

Use Omeka IDs for linked entities, separate literal/unresolved contributors,
return ambiguity candidates, and report matched seed IDs. Treat label matching
as discovery rather than identity resolution. Preserve all existing citable
detail tools and their public URLs.

### P2 — Discovery and response budgets constrain new tools

The unchanged measured surface is **8,329 estimated tokens / 27 stdio tools**
and **9,543 / 29 HTTP tools**, leaving just **457** below the HTTP budget.
The largest measured text response is about **14,974 tokens**. These are bytes/4
estimates, not actual model tokenization.

`textResult` includes the same payload as JSON text and `structuredContent`.
The benchmark measures both: wire result bytes are roughly twice text bytes.
Keep the text fallback for compatibility, but measure wire size separately from
model-visible text; host behavior determines what enters model context. Do not
assume every client pays exactly the same token cost.

Before adding several tools, define stable deployment profiles such as research,
discovery and visualization, with the current full profile remaining compatible.
Use app-only visibility for UI helper calls when appropriate, while remembering
that these tools can still occupy the server's raw discovery payload. A host
must implement visibility filtering for the model-context benefit to apply.
Measure each profile and use deliberate budgets instead of silently raising them.

### P2 — Packaging and transport coverage need a few operational additions

Keep the now-explicit modern stdio and HTTP tests alongside legacy clients.
Add modern HTTP header/envelope mismatch cases, oversized requests and concurrent
calls. Retain the Origin/Host protections already present. The in-process rate
limiter is a courtesy limit, not a distributed quota; bound its key count and
apply deployment quotas at the trusted proxy. `trustProxy` must remain opt-in.

Add LTS CI coverage, a Windows packaging lane for path/rename behavior, a clean
Docker build/run check and dependency-update PR automation if desired. Repeated
full crawls are appropriate for release verification, but rebuilding source
should be separable from recrawling data for reproducibility and faster iteration.

## Measured performance

[`benchmark-2026-10-05.json`](benchmark-2026-10-05.json) records the exact
arguments and snapshot manifest. Measurements used Node 24.19.0 on Windows,
the bundled snapshot fetched 9 September, full exposure, no live refresh and an
isolated empty cache. Each case has one first call followed by 30 sequential
samples through the SDK's in-memory transport. These are local end-to-end tool
latencies, not HTTP capacity estimates; cases share a process and warm caches.

| Case | Median ms | p95 ms |
| --- | ---: | ---: |
| Overview | 15.57 | 31.24 |
| Subject facets | 30.77 | 80.46 |
| Location facets | 10.01 | 18.01 |
| Decade timeline | 2.94 | 5.63 |
| Item keyword | 29.97 | 116.30 |
| Empty multi-filter query + relaxation work | 55.36 | 93.11 |
| Related entities | 11.26 | 16.88 |
| Publication full-text search | 12.37 | 22.59 |
| Search across all corpora | 55.05 | 73.90 |
| Same search restricted to projects | 1.41 | 1.89 |

Snapshot load measured 437 ms; server construction/close averaged 3.2 ms.
Heap use at the end of the run was 188 MiB without a forced GC, so it is not
a retained-memory or leak measurement. At this corpus size, targeted caches
and fewer repeated predicate evaluations are a better first investment than
external search infrastructure. Re-run before/after any performance change;
do not turn these machine-specific values into brittle CI timing assertions.

## MCP Apps: next iteration

The four existing apps are lightweight, self-contained SVG views with shared
DRE styling and text/structured-data fallbacks. Preserve those strengths. They
mostly render results, with hover titles; they do not yet support a full
interactive research workflow.

The initialization corrections in this change follow the official
[Apps typed contract](https://github.com/modelcontextprotocol/ext-apps/blob/main/src/spec.types.ts).
For further interaction, evaluate the current **`@modelcontextprotocol/ext-apps`
2.0.3** SDK, whose registry peers support MCP v2. It can replace the growing
handwritten bridge; bundle it locally and measure the added bytes before
adoption. The [official Apps overview](https://modelcontextprotocol.io/extensions/apps/overview)
and [SDK examples](https://github.com/modelcontextprotocol/ext-apps) cover
host-mediated tool calls and resource-backed views.

Remaining bridge work: resize notifications, teardown handling, request timeout
cleanup, tool-error/cancellation states and host context dimensions. No SDK was
added during this review. No claim of successful rendering inside every real
MCP host is made.

Code-level UI audit, provisional **12/20**:

| Dimension | Score / 4 | Evidence |
| --- | ---: | --- |
| Accessibility | 2 | SVGs have image labels; no equivalent detailed data table, and numeric detail relies partly on hover titles. |
| Performance | 3 | Small inline templates, no remote libraries/assets, no expensive animation; whole-result rerenders remain. |
| Responsive behavior | 2 | Fluid SVG width, but 9.5px labels on a 600-unit graph shrink to roughly 5px in a narrow chat panel. No alternate narrow layout or viewport meta tag. |
| Theming | 3 | Shared light/dark tokens and parent theme updates; no comprehensive host-style integration or measured contrast audit here. |
| Implementation integrity | 2 | Consistent AMIRA identity, but reproduced empty-state and edge-count errors misrepresent research evidence. |

Integrity verdict: the product-specific visual system is coherent; the graph's
data presentation fails correctness until the P1 findings are fixed. This is a
source and renderer audit, not WCAG certification. There are two P1 graph
presentation issues and three P2 UI groups: lifecycle/error handling, accessible
alternatives, and narrow-panel layout. The Impeccable detector could not start
because its engine was absent and its cache was not writable. There were no
committed UI screenshots, PRODUCT.md or DESIGN.md; no browser/host visual audit
was performed.

Prefer a ranked list/table in narrow panels, with an optional graph view. Provide
keyboard-focusable entity links, full labels and an evidence drawer. Never make
the graph the only way to access the data. Suggested UI follow-up order:
`/impeccable harden`, `/impeccable adapt`, then `/impeccable polish` after the
data-contract fixes. These can be addressed individually or together; a later
`/impeccable audit` should include real host rendering.

## Proposed tools and visualizations

These are concrete candidate designs, not additions to the current surface.
Prioritize one workflow at a time and measure retrieval quality and discovery
cost before expanding the catalog.

| Priority | Candidate | Research task and contract |
| --- | --- | --- |
| 1 | `resolve_entity` | Resolve a label/ID to typed authority candidates, with ambiguity, canonical name and `amira_url`. Could instead extend existing detail tools with ID inputs. |
| 1 | `get_entity_graph` | Return a bounded neighborhood from a typed Omeka ID, with typed nodes, relations and evidence IDs. Start with one hop and explicit node/edge caps. |
| 2 | `get_text_passages` | Search within selected publication/transcript IDs and return bounded excerpts with original offsets, matched fields and source links. Avoid repeatedly fetching 25,000-character windows to locate a phrase. |
| 2 | `compare_collections` | Apply the same filters to selected projects/collections and compare types, languages, dates and coverage. Include denominators and missingness; do not equate collection size with research importance. |
| 2 | `get_data_quality` | Report corpus coverage, unresolved authority links, missing dates/coordinates/full text and refresh status. Useful to researchers and maintainers; can begin as an overview option. |
| 3 | `get_snapshot_changes` | Explain additions/changes/removals between retained generations. Requires safe generation retention first. |

**Graph contract.** Nodes should contain a stable typed ID, type, canonical label
and citation URL. Distinguish explicit metadata relations (`authored`,
`contributed`, `member_of`, `located_in`) from derived co-occurrence. Derived
edges need distinct source-record counts by corpus, evidence links, matching
rule and truncation flags. Include the snapshot identity. Preserve unresolved
literals distinctly; never merge people solely by a folded name.

Example initial limits: depth 1, 100 nodes, 200 edges, five example evidence IDs
per edge, plus a separate paginated evidence drill-down. These are proposed
design values. Raise them only after measurement. An app expansion should call
the server through the host and update the selected node/evidence context; it
must not imply that co-occurrence establishes collaboration or causation.

**Map.** Reuse existing location coordinates and hierarchy. Start with a compact
place table and optional map, showing geographic missingness. Do not place a
country-only record at a city or silently treat a centroid as an observation.
`list_locations` already supplies useful data; a new map tool may be unnecessary.

**Timeline.** Add brush/filter interaction and an evidence list using the same
research-item selector as search. Keep the current explanation that a date-range
item contributes to multiple years. The chart must also disclose when pagination
shows only part of a histogram; do not infer complete temporal coverage from a
single capped page.

**Bibliography explorer.** Compose the existing publication filters, facets,
detail and export tools into an app. Provide a selected-record panel and bounded
RIS/BibTeX/CSL-JSON export. This is a stronger near-term workflow than adding a
second publication-search API.

For each app, keep concise findings in text/structured content and use tool-result
metadata for presentation-only state when supported. Source evidence needed for
the model's claims must remain model-visible. Check actual host support through
the [extension support matrix](https://modelcontextprotocol.io/extensions/client-matrix).

## Refactoring sequence and acceptance criteria

1. **Correctness first:** fix distinct-record graph counts, publication-only
   rendering and snapshot API provenance. Add focused regression fixtures and
   keep the public tool names stable.
2. **Shared query layer:** extract research-item predicates and range checks into
   a selector analogous to `publicationQuery.ts`; have search, timeline,
   comparisons and map/graph filters reuse it. Split `_shared.ts` into response,
   pagination, text-window and summary modules by responsibility. Separate
   OpenAI search scoring from fetch rendering only when touching those paths.
3. **Snapshot-owned indexes:** measure search/facet improvements, result parity
   across all exposure levels, startup cost, memory and refresh invalidation.
   Optimize the current implementation before evaluating BM25 against a dated
   multilingual retrieval set. Do not replace source-grounded keyword matching
   with unmeasured semantic search.
4. **Durable snapshots and operations:** generation pointer/lock, provenance,
   broader freshness, refresh status and cancellation. Fault-inject disk errors
   and upstream changes; prove the last usable generation survives.
5. **One evidence-backed app:** introduce typed graph results and a responsive
   graph/list/evidence view, preferably with the official Apps SDK. Gate payload
   size, ambiguous identities, host initialization, light/dark rendering,
   keyboard use and plain-text fallback.

Keep publication exports, citation generation and full-text windowing shared;
these are already useful abstractions with meaningful tests. Avoid adding OAuth,
sampling, elicitation, subscriptions or durable tasks simply because the protocol
supports them. The current public, local-snapshot queries do not require those
features. Tasks become relevant if future tools launch genuinely long-running
exports or analysis; the [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)
is an optional capability, not a prerequisite for this server.

## Validation and limits

- TypeScript check, strict build and **112 unit tests passed**.
- Actual stdio/HTTP smoke suites, modern protocol tests, skill checks and
  manifest validation passed.
- Full `prepack-mcpb` passed using the bundled snapshot and an isolated cache;
  response budgets matched the committed baseline. A real temporary MCPB archive
  was built successfully (about 6.8 MB).
- All direct dependencies are current; production audit passes. Full audit
  fails only on the unresolved MCPB/node-forge advisory described above.
- No release, commit, push, deployment or remote data mutation was performed.
- Docker was unavailable on PATH; no container build/run was executed. No live
  Omeka recrawl or live API suite was needed for these local protocol changes.
  Collection examples and performance results are dated snapshot observations.
- The starting 110 tests passed before changes. Added tests cover previously
  untested interoperability behavior; broader retrieval effectiveness still
  needs a blind, multilingual evaluation with judged answers and citations.
