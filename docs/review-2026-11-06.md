# Refactoring review — amira-mcp-server 1.34.0

Review of `main` at `1da83c7` (v1.34.0), 6 November 2026.

**Status: implemented** on the branch that adds this file; `CHANGELOG.md` (Unreleased) says what
changed. Where the implementation took a different route than proposed here:

- **M7:** schema noise was dropped (`$schema`, `propertyNames`, output `additionalProperties: false`)
  instead of loosening the nested output schemas.
- **M10:** the view scripts moved unchanged into `src/ui/views/*.js`, where they are linted and
  typechecked, instead of being rewritten as modules.
- **L3:** composite actions replace a reusable workflow.
- **M6:** the record pivot keeps `seed_label` and the top-level `amira_url`.

Like the October reviews, retire this file once the work has shipped.

**Scope.** All of `src/` (tools, snapshot lifecycle, query and matching code, the `src/ui/` app
views), `scripts/`, `test/` and `.github/workflows/`. Recommendations follow the rules in
`ROADMAP.md` ("Decisions in force") and `CONTRIBUTING.md`: no model at request time, cite by
`amira_url`, token discipline (D10), stable tool names (D7), and a fixed tool surface per profile.

**Baseline, measured in this worktree** (fresh `npm ci` and `npm run fetch-data`, snapshot of
2026-11-06, 29 MB, semantic build `semantic-embeddings-v1-35`):

**How to read a finding.** Each one gives the file and line, the problem, a concrete change, its

keep in sync, weighed against effort (S < ½ day, M ≈ 1–2 days, L > 2 days). Lines are those of
`1da83c7`.

## What I would do first

Ranked by value against effort and risk:

1. **Q1. Make CI actually run the packaging allowlist test, and make the Windows step fail when it
   should.** Two small YAML edits close a gap that already bit v1.31.0.
2. **Q2. Make `weigh --check` fail on a probe it stopped measuring, and stop `--update` from
   baselining failed probes.** D10 is only as strong as this gate.
3. **M1. Give record kinds one registry** (`src/recordKinds.ts`). It removes the kind switch now
   copied in 8 places, and it is the base for M2 and M3.
4. **M2. Write one "what a record links to" function and one ref tally.** This replaces the three
   aggregation loops in `related.ts` and the copies in `similar.ts` and `semanticMap.ts`.
5. **Q3. Build `semanticIndex` from a single id→record map.** That cuts 170 ms on the first semantic
   call; warm it when the store loads.
6. **M4. Stop `get_snapshot_changes` from keeping up to three extra full snapshots in memory for
   the life of the process**, and from parsing them on the request path.
7. **Q5. Read only the manifest in `writeSnapshotAtomic`.** This removes two of the three full
   snapshot parses that block the event loop during a live refresh.
8. **M3. Parse typed ids per tool in one helper**, with a wrong-kind hint.
9. **Q6. Give `cachedRecent` one bound per namespace**, so `edges:` entries really are limited to 64.
10. **M6. Align the response shapes of the semantic tools, and drop the duplicate fields in the
    record pivot.**

Order matters: M1 before M2 and M3. Every quick win is independent.

## Quick wins (S effort, low risk)

### Q1. CI never runs the real-bundle allowlist test; the Windows packaging step ignores early failures

- **Where.** `.github/workflows/ci.yml:67-74`, `test/unit/packaging.test.mjs:153-157`.
- **Problem.** The test "the real repository packs to an allowlisted .mcpb" skips itself when
  `data/` is absent.
  - In the test matrix, `node scripts/test.mjs unit` (line 68) runs before
    `node scripts/fixture-snapshot.mjs` (line 72), so `data/` is never there.
  - The smoke job has real data but runs no unit tests.
  - So the allowlist that `.mcpbignore` relies on is checked only by `prepack-mcpb`, at release or
    refresh time.
  - Separately, the Windows step "Windows fixture packaging check" has no `shell:`, so it runs
    under pwsh. GitHub's pwsh wrapper exits with the last command's code only, and a native
    command's non-zero exit does not stop the script. A failing `fixture-snapshot.mjs` is therefore
    hidden as long as `pack` succeeds. The inline `node -e` check (lines 83-94) does not require
    any `data/` entry.
- **Change.** Add `shell: bash` to the Windows step. Run `fixture-snapshot.mjs` before the unit
  tests in the Windows lane (or add `node --test test/unit/packaging.test.mjs` after it), and add
  the same line to the smoke job after `fetch-data`. The inline `node -e` block, a weaker copy of
  the test, can then go.
- **Risk.** Low.
- **Test.** The CI log shows the packaging test as `ok`, not `# SKIP`. Make `fixture-snapshot` fail
  on a scratch branch and confirm the step goes red.

### Q2. `weigh --check` lets a probe drop out silently; `--update` writes failed probes as 0 tokens

- **Where.** `scripts/weigh.mjs:396-398` (a missing probe is only a note); `:548-551` (skipped
  probes are only printed); `:572-584` (`--update` writes every probe, failed ones included);
  `:385` (`!was` treats a 0-token baseline as a new probe).
- **Problem.** Probe discovery depends on the data: a hard-coded `"Ulli Beier"`, the first
  publication with full text, seeds that have neighbours. A data refresh can remove
  `get_similar_items@max`, `get_entity_graph@max` or `get_publication@fulltext` from the D10 gate
  without anything going red. A probe that failed during `--update` is stored as 0 tokens and is
  never compared again.
- **Change.**
  - Under `--check`, fail when a probe id in the baseline is missing from the run, or when
    `skipped` is non-empty.
  - Refuse `--update` while there are failures.
  - Take the person probe from discovery, not a hard-coded name.
  - Add the probes that are missing today (see T3):
    - `find_related@record` (the semantic pivot, not probed at all);
    - `get_semantic_map@group` (group mode at `limit: 100`);
    - `get_publication@fulltext+similar` (the largest detail response, ≈ 30k + 3k chars).
- **Risk.** Low. A future refresh may go red, which is the point.
- **Test.** In `test/unit/budget.test.mjs`: `checkResponses({}, { x: { tokens: 1 } })` must return
  a failure, and an `--update` payload built with a failed probe must throw.

### Q3. The semantic index takes 170 ms to build on the first request

- **Where.** `src/semantic.ts:337-351` (`semanticRecord`), `:364-388` (`semanticIndex`).
- **Problem.** `semanticRecord` allocates six closures on every call and tries up to six kinds.
  `semanticIndex` calls it for every source (3,331) and every stored neighbour (about 60 per
  source): roughly 200,000 calls. The build runs synchronously on the first semantic request, and
  again after every live refresh.
- **Change.** Build one `Map<number, SemanticRecord>` from the six corpora (about 11k entries),
  either in `semanticIndex` or as `store.cached("semantic:records")`, and resolve through it.
  `semanticRecord(store, oId, kinds)` becomes a lookup followed by a kind check. Then warm the
  index once a store is constructed (at startup and after a refresh), off the request path. M1
  gives this map for free.
- **Risk.** Low. Same results.
- **Test.** The existing `semantic.test.mjs` cases still pass. Add a property test: for every
  record, the map lookup equals the old per-kind probe.

### Q4. Code that misleads readers

- `src/tools/responses.ts:32`: `STRIP_CHARS` contains the literal, invisible Private-Use characters
  U+E000 and U+F8FF, so the source reads `\u007F-\u{F0000}`, which looks like a range from DEL to
  plane 15. Write them as `-`. (`od -c` shows bytes `356 200 200 - 357 243 277`.)
  Test: the existing `scrub` test, plus one that `scrub("é")` is unchanged.
- `src/tools/openai.ts:12`: "the stdio .mcpb keeps its 34-tool surface" is out of date; there are
  36 (`register.ts:22`). The imports at lines 1-2 sit above the header comment.
- `src/tools/policy.ts:31-34, 121-126`: `CALL_DEADLINE_MS` cannot interrupt a handler, because
  every handler is synchronous once `ensureStore()` resolves. A timer cannot fire while the event
  loop is blocked, and the resolved work promise wins the race. The deadline only covers the first
  store load and `retainedSnapshots`' disk reads. Say so in the comment, or use M4 and Q5 to keep
  heavy work asynchronous.
- `src/tools/facets.ts:41-46`: in `countRefs`, `if (!key …)` can never be true. The line
  `if (rec.o_id == null && ref.o_id != null)` cannot run either: a row keyed by label never
  receives a ref with an id. Delete both. M2 replaces the function anyway.

### Q5. A live refresh parses the 29 MB snapshot three times, and up to four, on the event loop

- **Where.** `src/snapshot.ts:491` (`loadSnapshot(destDir)` only to compare `fetchedAt`), `:496`
  (verify the new generation), `:500` (a second identical load of the legacy layout), then
  `src/data.ts:434` (load again to serve).
- **Problem.** Each load is about 240 ms of synchronous `JSON.parse` in a serving process; the
  stringify in `writeSnapshot` adds more. Line 500 repeats line 491 whenever there is no pointer.
- **Change.**
  - Add `readManifest(dir)`, which follows the pointer and reads only `manifest.json`, and use it
    at `:491`.
  - Reuse `existing` as the legacy snapshot at `:500`.
  - Make `writeSnapshotAtomic` return the verified `CrawlOutput` from `:496`, so `data.ts:434`
    stops loading it a third time.
- **Risk.** Low. The verification still parses what was written.
- **Test.** `refresh.test.mjs` already covers publish and hot swap. Add a spy, or count `readFile`
  calls through a temporary wrapper, to assert one full load per publish.

### Q6. `cachedRecent` is one LRU shared by every namespace, each with its own `max`

- **Where.** `src/data.ts:105-116`. Callers: `entityGraph.ts:128` (`edges:`, max 64), `similar.ts:36`
  (`semantic-links:`, max 256), `semanticMap.ts:46` (`semantic-group:`, max 128).
- **Problem.** Eviction removes at most one entry per call, and only when `size > max` for the
  current caller. Once `semantic-links:` calls have grown the LRU to 256 entries, an `edges:` call
  with max 64 evicts one entry and leaves 255. Edge lists are the heaviest entries, so in practice
  they are bounded by the largest `max` any caller uses, not by 64.
- **Change.** `cachedRecent(namespace, key, build, max)` with one `Map` per namespace, and evict in
  a `while` loop.
- **Risk.** Low.
- **Test.** A unit test on `DataStore`: interleave 300 `a:` keys at max 256 and 100 `b:` keys at
  max 64, then assert at most 64 `b:` entries remain.

### Q7. Inconsistent error codes and ad hoc limit clamps

- `invalid_arguments` (`semanticMap.ts:104`) against `invalid_argument` (`policy.ts:121`). Keep the
  singular, and add a test listing every error code (grep `errorResult("…"`) against an allowlist.
- Three hand-written clamps duplicate `capLimit`: `related.ts:100` (which also skips `Math.floor`),
  `openai.ts:399` and `openai.ts:442`. Replace them with `capLimit`.
- The contributor label `` `${c.name}${c.role ? ` (${c.role})` : ""}` `` is written six times:
  `summaries.ts:59, 163`, `resources.ts:87`, `openai.ts:133, 278`, `citation.ts:169`. Add
  `creditLabel(c)` to `matching.ts`. `resources.ts:93` also re-implements `mediaTypes()` from
  `summaries.ts:39`.

### Q8. A latent false match in `find_related` `entity_type=project`

- **Where.** `src/tools/related.ts:138`.
- **Problem.** `equalsCI(String(store.projectOf(it)?.o_id), value)`: for an item with no project,
  `String(undefined)` is `"undefined"`, so `value: "undefined"` matches every project-less item. In
  today's snapshot every item has a project (0 matches, measured), so it is latent. The same line
  also calls `projectOf` twice.
- **Change.** `const p = store.projectOf(it); return (p && (String(p.o_id) === value ||
  equalsCI(p.dre_id, value))) || containsCI(it.project?.label, value);`
- **Test.** A fixture item without a project must not match `"undefined"`.

## Medium refactors (M effort)

### M1. One registry of record kinds

- **Problem.** Each module has its own "which corpus, which lookup, which tool, which prefix" table
  or switch for a record kind:

  | Site | What it encodes |
  |---|---|
  | `typedIds.ts:225-236` | prefix → kind |
  | `semantic.ts:43-51, 337-351` | producer type → kind and corpus; kind → lookup |
  | `tools/similar.ts:45-67` | kind → links |
  | `tools/semanticMap.ts:49-60` | kind → subjects, countries, projects |
  | `tools/related.ts:236-261` | kind → counted links |
  | `tools/research.ts:169-172` | kind → text record (`get_text_passages`) |
  | `resources.ts:151-160, 246-247` | kind → `get_*` tool; kind list for completion |
  | `tools/openai.ts:108-365` | kind → `fetch` document, one 250-line function with 6 branches |
  | `entityGraph.ts:12-13, 46-51` | entity types → corpus rows |

  Adding a kind (organisations to the semantic space, say) means editing all of them, and they
  already disagree. `resources.ts:246` lists `organisation`; `SEMANTIC_KINDS` names sections
  `section`, while `openai.ts` emits `research_section`.
- **Change.** Create `src/recordKinds.ts`:

  ```ts
  interface RecordKindDef<R> {
    corpus: CorpusName; prefixes: string[]; byOId(store, oId): R | undefined;
    title(r: R): string; detailTool?: string; fetchPrefix?: string; semantic?: boolean;
    links?(store, r: R): RecordLinks;   // see M2
  }
  export const RECORD_KINDS: Record<RecordKind, RecordKindDef<any>>;
  ```

  - Add `DataStore.record(kind, oId)` and `DataStore.recordByOId(oId)` (one map, which also serves
    Q3).
  - Derive `PREFIXES`, `SEMANTIC_KINDS`, `RECORD_TOOLS`, the resource completion list and the
    `fetch` routing from the registry.
  - `fetchDoc` then becomes a table of six small renderers.
- **Risk.** Medium. The change touches many tools, but behaviour is unchanged.
  `tools-coverage.test.mjs` and `contract.test.mjs` cover the visible surface.
- **Test.** One table-driven test: every kind round-trips prefix → parse → lookup → `amira_url`, and
  every kind with a `detailTool` serves `amira://record/<kind>/<id>`.

### M2. One record→links function and one ref tally (the three aggregation loops)

- **Problem.** Three modules each do "fetch the record by kind with `!`, pull out
  subjects/places/people/project, then count distinct refs":
  - `related.ts:150-157`, `:239-261` and `:302-309`: three copies of the research-item count
    block, plus two literal copies of the six `Map<string, Count>`.
  - `similar.ts:35-70` (`linksOf`) and `semanticMap.ts:45-72` (`describeGroup`).
  - Key normalisation for an unlinked ref differs between seven sites: `fold` in `related.ts:64`,
    `similar.ts:41`, `semanticMap.ts:32`; `toLowerCase` in `facets.ts:41, 148`; raw label in
    `researchItemQuery.ts:103`; `nameKey` in `people.ts:243`. As a result `list_subjects` and
    `list_locations` count "Côte d'Ivoire" and "Cote d'Ivoire" (both unlinked) as two rows, while
    `find_related` merges them.
  - There are also three ref counters: `countRefs` (`facets.ts:35`), `countRecord`
    (`related.ts:61`) and `tally` (`semanticMap.ts:26`).
- **Change.**
  - `refKey(ref)` in `matching.ts`, with `fold` as the single rule (`people.ts` keeps `nameKey` for
    person names on purpose; document that).
  - `class RefTally { add(refs, field?) ; top(n) }`, which replaces all three counters.
  - `recordLinks(store, record)` in the M1 registry, returning
    `{ subjects, places, countries, people, projects, sections, formats }`, and cached per record
    with `cachedRecent("links", …)`.
  - `related.ts` then reduces to "choose the seed records, tally their links", for all three
    pivots. `similar.ts` intersects two link sets. `semanticMap.ts` tallies a group.
- **Risk.** Medium. Counts in `list_subjects` / `list_locations` can change by a few rows where
  accents differ; that is the fix, so call it out in the CHANGELOG.
- **Test.**
  - Golden counts for `find_related` on the fixture, for all four entity pivots plus `record`,
    captured before and after (they must be identical).
  - A fixture pair "Côte d'Ivoire" / "Cote d'Ivoire" collapsing to one row in `list_locations`.

### M3. Typed-id parsing for the detail tools

- **Where.** `Number(stripTypedId(String(id), ["…"]))` at `media.ts:147, 236`,
  `organizations.ts:243`, `people.ts:190`, `researchSections.ts:64`, and
  `stripTypedId(String(id), […])` at `projects.ts:105`, `publications.ts:108`,
  `researchItems.ts:130`. "Section by name or id" is also resolved three times:
  `researchItemQuery.ts:190`, `projects.ts:61`, `researchSections.ts:64`.
- **Problem.** Passing `video:39218` to `get_podcast` returns "No podcast with id video:39218",
  where a "this is a video id; use get_video" hint would let an agent recover in one step.
  `similar.ts:129-149` (`resolveSemanticSeed`) has a third, separate implementation.
- **Change.** Add `recordId(raw, kind): { key: string; oId: number | null } | { wrongKind:
  RecordKind }` to `typedIds.ts`, and a shared `wrongKindError(kind, tool)` naming the M1
  registry's `detailTool`. Add `store.resolveSection(nameOrId)`.
- **Risk.** Low. This adds information to existing `not_found` errors (code unchanged).
- **Test.** A table test over every `get_*` tool with a typed id of another kind, expecting

### M4. `get_snapshot_changes` keeps whole snapshots alive and parses them on the request path

- **Where.** `src/tools/research.ts:33-68` (module-level `historyCache`), `:70-90` (`snapshotDiff`
  compares `JSON.stringify(prev)` against `JSON.stringify(next)` for every record).
- **Problem.**
  - The first call loads up to three retained generations plus the bundled snapshot. That is about
    240 ms of synchronous parse each, with full texts and transcripts.
  - It then keeps all of that in a module global until the generation list changes. On the public
    HTTP server, one call can roughly quadruple resident memory for the life of the process. The
    measured heap with one snapshot is about 200 MB.
  - The cache is not tied to the `DataStore`, so it outlives a refresh until the next call
    notices the new key.
- **Change.** Diff fingerprints, not data.
  - At write time, `writeSnapshot` adds `fingerprints.json`: per corpus, `o_id → [sha1(record), title]`
    (a few hundred KB). Older generations without it fall back to computing fingerprints once.
  - `retainedSnapshots` keeps only fingerprints, cached per generation id.
  - The served store computes its own fingerprints lazily through `store.cached`.
- **Risk.** Medium. It touches the snapshot layout. The file is optional, so no schema bump is
  needed (`loadSnapshot` ignores unknown files).
- **Test.**
  - `output-schemas.test.mjs:158` already exercises the "ready" path; add an assertion that
    `added`, `updated` and `deleted` are identical with and without the fingerprints file.
  - A memory check in a smoke test: heap after `get_snapshot_changes` under 1.5× the heap before.

### M5. The fold cache is global and keyed by text

- **Where.** `src/text.ts:58-60, 92-98`; cleared at `data.ts:437`.
- **Problem.** `foldedCache` and `offsetCache` are module-level `Map`s keyed by large strings. The
  refresh clears them after the swap, but a request still running against the old store can add
  old-snapshot texts right after the clear. Those then stay reachable until the next refresh,
  about 12 MB of publication full text plus transcripts. It is also hidden coupling: `data.ts`
  has to know to clear a cache that `text.ts` owns.
- **Change.** Hang the caches on the `DataStore` (a `WeakMap<DataStore, Map>`, or
  `store.cached("fold")`), and pass the store, or a `Folder` it owns, to the few callers of
  `foldCached`. `clearFoldCache` then disappears.
- **Risk.** Low to medium (signature changes in `text.ts` / `matching.ts`).
- **Test.** After a hot swap in `refresh.test.mjs`, the old store's fold cache is unreachable:
  check the size of a `WeakRef`-observed map, or simply that the new store's cache starts empty.

### M6. The semantic tools' response shapes, and duplicate fields

- **Problem.** The same "record reference" has four shapes:
  - `similar.ts:88`: `{ id, omeka_id, type, title, amira_url }`.
  - `semanticMap.ts:23`: `{ title, type, omeka_id, amira_url }` (no `id`).
  - `related.ts:274-275` `closest`: `{ title, type, score, omeka_id, amira_url }`.
  - `related.ts:267` `seed`: the `similar.ts` shape.

  The `record` pivot also returns the seed title twice (`seed_label` and `seed.title`) and the seed
  `amira_url` twice (`seed.amira_url` and top-level `amira_url`). The `space` object is built in
  three places (`similar.ts:188`, `semanticMap.ts:77`, `related.ts:270`), and so is the
  "semantic_unavailable" error (`similar.ts:177`, `semanticMap.ts:99`, `related.ts:218`).
- **Change.**
  - Export `semanticRef(r)` and `semanticSpace(index)` from `semantic.ts`, plus one
    `semanticUnavailable(suggested)` result.
  - Drop `seed_label` from the record pivot. Keep top-level `amira_url`, which the other pivots
    share, and drop it from `seed`.
  - D7 protects tool names, not field order. A field that disappears from a 1.34.0 response is a
    behaviour change, though, so note it in the CHANGELOG.
- **Risk.** Low.
- **Test.** An `outputSchema`-style zod check in `semantic.test.mjs` asserting one ref shape across
  `get_similar_items`, `get_semantic_map` (group mode), `find_related record` and `include_similar`.

### M7. Tool-surface token cost: output schemas are 23% of the surface

- **Measured.** 13,028 of 55,470 chars on HTTP (about 3,250 tokens per turn) are output schemas on
  11 tools. The largest:

  | Tool | Output schema (chars) | Input schema (chars) |
  |---|---|---|
  | `get_entity_graph` | 2,541 | 846 |
  | `get_collection_overview` | 1,929 | 119 |
  | `resolve_entity` | 1,295 | — |
  | `compare_collections` | 1,137 | — |
  | `get_snapshot_changes` | 1,038 | — |
  | `list_years` | 953 | — |

- **Options**, which need your decision because they trade contract strictness for tokens:
  - (a) Keep a precise top level, but type deep arrays loosely: `edges: z.array(z.object({}).passthrough())`
    in `get_entity_graph`, and `counts` maps instead of per-corpus fields in
    `get_collection_overview`. Rough estimate: −1,500 to −2,500 chars.
  - (b) Advertise output schemas only on the tools a host renders as an app. The policy already
    keeps `structuredContent` for those, through `_meta.ui`, without an output schema.
  - (c) Leave as is. Under the per-turn budget, the surface is still within its limits.
- **Risk.** Low for (a), medium for (b): ChatGPT's `search`/`fetch` contract expects output
  schemas, so keep those two.
- **Test.** `output-schemas.test.mjs` keeps validating responses. `budget.test.mjs` records the new
  surface. Run `npm run weigh -- --update` and review the diff.

### M8. Per-request server construction on HTTP

- **Where.** `src/httpApp.ts:222` creates a server per request (stateless by design, SEP-2567).
  Every `register*Tools` builds its zod schemas inline, and `applyToolPolicy` wraps every schema.
- **Measured.** 2.8 ms per request before any work, and `tools/list` repeats the zod→JSON-Schema
  conversion for every server.
- **Change.** Hoist each tool's `inputSchema`/`outputSchema` to module constants, so construction
  only wires handlers. Memoise the advertised JSON Schema per (schema, guidance) in a `WeakMap`
  inside `withJsonSchema`. Keep a fresh `McpServer` per request.
- **Risk.** Low.
- **Test.** A micro-benchmark in `scripts/benchmark.mjs` (e.g. 200 constructions under 1 ms each),
  with the `tools/list` golden output unchanged (see the roadmap's golden-files item).

### M9. Data refreshes keep semantic neighbours only until the next forced crawl

- **Where.** `src/snapshot.ts:372-381` (`isStale`), `src/data.ts:432`.
- **Problem.** `isStale` notices a moved full-text pin, but not a newer corpus-vector release.
  A new `semantic-embeddings-v1-<n>` is therefore picked up only when Omeka changes or the weekly
  forced crawl runs. That is acceptable, but undocumented. Conversely, when a crawl cannot verify a
  release, the carried-over neighbours (`data.ts:432`) were computed against the previous snapshot.
  New records then show "not in release", which is honest. No test covers either carry-over path,
  for neighbours or for the full-text map (`data.ts:430`).
- **Change.**
  - Document the cadence in the README's refresh section.
  - Optionally record `semanticNeighbours.tag` in the probe comparison when the setting pins a tag
    that differs from the manifest's.
  - Add the two missing tests (see T2).
- **Risk.** Low.

### M10. App views are ES5 strings that bypass typecheck and lint

- **Where.** `src/ui/*.ts`. Each view's `SCRIPT` is a `String.raw` template, about 1,000 lines in
  total, built by string concatenation into `innerHTML`. There is no type checking and no lint
  beyond the 17 `noUselessStringRaw` infos. The evidence list markup ("N matching records",
  `<ol start>`, "Next records") is copied in `graph.ts:82`, `map.ts:46` and `timeline.ts:109`.
  Escaping is consistent (`window.amiraApp.esc`). The values left unescaped are numbers or
  internal constants (`shell.ts:192` `p.name`), and `href` takes only server-built `amira_url`s.
  No XSS found.
- **Change.** Move each view script into a real `src/ui/views/<name>.ts`, bundled by esbuild like
  the bridge already is (`scripts/build.mjs:56-62`), with a shared
  `evidenceList(target, data, moreId)` in the shell.
- **Risk.** Medium. The page budget and the gzip bootstrap must stay within `apps.test.mjs`'s
  budgets.
- **Test.** `apps-render.test.mjs` (happy-dom) already renders every view. Keep it unchanged as the
  oracle.

## Larger restructurings (L effort)

### L1. Split `related.ts` by pivot, on top of M1 and M2

`find_related` is 261 lines in one module, with three pivots that share only output formatting.
Once M2 lands, `src/tools/related/` can hold `entity.ts` (subject, location, person, project),
`fulltext.ts` and `meaning.ts`. Each returns `{ seedRecords, extra }` for one shared renderer
(`relatedLists(tally, limit)`). The value is in review cost: each pivot's matching rule (the
`MATCHING` table) then lives next to its code. **Risk:** medium. **Test:** the golden counts
from M2.

### L2. A request-path budget for synchronous work

Several first calls run 100–250 ms of synchronous CPU on the event loop: `semanticIndex` (Q3),
`graphIndex` (`entityGraph.ts:33`), `fulltextIndex`, and `retainedSnapshots` (M4). On the HTTP
server, other clients' requests wait behind them. Combined with Q4 (the deadline cannot interrupt
synchronous work), the robust fix is to warm every `store.cached` index when a store is constructed
(startup and after a refresh), in `setImmediate` slices like `computeNeighbours` already does
(`semantic.ts:196-199`). Requests would then never pay for an index. **Change:** a `warm(store)`
list of index builders in `data.ts`, awaited before `current` is swapped on refresh. **Risk:**
medium: refresh takes longer, but serving never stalls. **Test:** time the first call of each
indexed tool after `ensureStore()` and assert under 20 ms on the fixture.

### L3. One reusable bundle workflow for release and refresh

`release.yml:56-107` and `refresh-data.yml:43-108` run the same pipeline: checkout, setup-node,
`npm ci`, audit, `fetch-data`, `prepack-mcpb`, live tests, pack. The project also builds twice,
because `fetch-data` builds and `prepack-mcpb` cleans and rebuilds. Setup-node plus `npm ci`
appears nine times across the workflows. Factor in two steps:

- a composite action `setup-node-deps`;
- a `workflow_call` workflow `_bundle.yml` that outputs the artifact, with each caller keeping its
  own gates (release: guard, notes, image, skill zip; refresh: signature check).

Add a `prepack-mcpb:ci` script without `clean`. Separately, consider caching `data/` in the CI
smoke job, keyed on the transform sources and the ISO week. Today every push and PR crawls the
live Omeka API, a network dependency in what D2 makes an offline-first project. **Risk:** medium
(release path; test it with `workflow_dispatch`). **Test:** both dispatch runs produce identical
artifact lists.

## Checked and found fine

- **Cache keys and exposure.** Every `store.cached` entry whose content depends on exposure keys on
  `exposureLevel()`: `overview:`, `ranking:`, `publication-meta:`. The others are gated before the
  cache (`quality`, the semantic and entity indexes) or hold no gated content. Every cache lives on
  the `DataStore`, so a hot swap invalidates it, except the fold cache (M5) and `historyCache`
  (M4).
- **The snapshot lifecycle.** The crawl-time consistency window, the generation pointer, the
  writer lock and the 24 h grace period hold up. A crawl that finishes late cannot overwrite a newer
  generation (`snapshot.ts:494`).
- **Semantic integrity.** The release is verified (checksum, dimensions, norms), lists are filtered
  to the served snapshot at load, low-signal records are excluded, and `computeNeighbours` yields
  every 4 rows. Neighbours are computed after the consistency probe (`snapshot.ts:335`).
- **Workflows.** Least-privilege `permissions:`, SHA-pinned actions, `persist-credentials: false`,
  and untrusted values passed through `env:`.
- **The HTTP app.** Origin and Host validation, a bounded limiter, constant-time bearer comparison,
  and IPv6 /64 bucketing.
- **Type safety.** No `any` in `src/`. Most of the non-null assertions are on typed-array indexing
  in `semantic.ts`, where they are correct. The `!` after kind dispatch (`similar.ts:46-66`,
  `related.ts:239-259`, `semanticMap.ts:52-57`) disappears with M1 and M2.

## Not recommended

- **Merging `fulltextIndex` and `semanticIndex`.** Both are "an optional enrichment filtered to the
  snapshot", but their data and provenance differ, and a shared abstraction would hide the
  rights-related caveats that sit in `fulltextMaps.ts`.
- **Removing the `id` + `omeka_id` pair from summaries to save tokens.** It is the project-wide
  convention: clients and the skill rely on both, and the saving per row is small.
- **A new tool for any of the above.** All of it fits within existing tools (D7, D10).
